## 💡 经验教训

### 1. 性能声明必须有实测证据
**epi3-01 声称「INP 降低 60%」却无验证证据，code review 被 defer。**

- 影响：性能收益无法量化，说服力不足
- 应对：epi3-03 用 PerformanceObserver（`first-input`）采集真实 INP 数据补足

### 2. `key={index}` 是 reconciliation 隐患
**epi3-02 初版虚拟列表用 index 作 key，导致展开/折叠后节点错位。**

- 影响：文件项 reconcile 错误，可能出现串位/闪烁
- 修复：改用 `item.file.path` 作为稳定 key

### 3. 样式锚定必须与常量一致
**ITEM_HEIGHT=28 常量与 CSS 实际行高脱节，滚动定位偏移。**

- 修复：`.file-item` 显式设置 `height: 28px`，并钳制 scrollTop

## ✅ 总结

Epic EPI3 完成搜索并发、文件树虚拟滚动与复杂操作并发处理，并以实测 INP 数据（p75 ≤ 40ms）验证了响应性收益。

**关键经验：**
1. **证据先行** - 性能声明必须可复现、可量化
2. **key 决定 reconciliation 正确性** - 稳定业务标识优于 index
3. **startTransition 有边界** - 只包同步状态更新，不包异步/命令式 API

**待改进领域：**
1. 幽灵文本 transition 取消机制
